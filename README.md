# ShopPilot

跨境电商选购 Agent。买家用自然语言描述需求（预算、用途、收货地），Agent 调用商品检索、品类知识、偏好记忆和交易工具，页面实时渲染回答、商品卡和确认单。

和「聊天框里接一个大模型」的区别在于：购物是有状态的、有副作用的、需要长期记忆的。用户会改预算、会重复点、会隔天回来接着问；而「下单」这种危险操作绝不能由模型直接执行。

这个项目解决的问题基本都在这些地方。

```
React (AG-UI Client) ──SSE──> FastAPI ──> Orchestrator ──> MainAgent
                                                  │            ├─ 检索/品类/偏好/交易工具
                                                  │            └─ task_dispatch → SearchAgent / TradeAgent
                                                  ├─ SQLite（会话、订单、偏好、Skill）
                                                  └─ Qdrant（商品与知识向量）
```

业务分层采用 DDD 洋葱结构：`domain` 定义实体与端口，`application` 放用例与编排，`infrastructure` 实现数据库/模型/检索适配，`presentation` 是最外层 FastAPI。`composition.py` 用同一套装配同时启动 API 进程与独立 worker——这是为了不出现「两个入口两套行为」。

## 一、为什么需要上下文治理

一个多轮选购会话，单轮就可能塞进十几件商品的完整 JSON，几轮下来上下文就被工具返回值撑满了。

**做法**（`app/infrastructure/context_governance.py`）：

- 商品软预算 6000 token，工作上下文目标 48000 token
- **先裁剪再摘要**：先删展示冗余（诊断信息、重复结果），仍超限才做摘要
- **裁剪资格**：一批新结果至少要**被模型成功读取过一次**，且已离开最近的完整轮次，才允许被裁剪——否则等于模型还没看到就被删了
- **受保护内容**：用户约束、已选商品、不同目的地/币种的报价、历史比价，不参与裁剪
- 被裁剪的旧结果保留**证据引用**，可按批次、商品位置、SKU、字段组回查

**结果**：36 次长对话对照实验中，实际输入 token 下降 35.85%（该数字包含摘要与回查本身的消耗，不是纯省下来的量）。

**代价与取舍**：裁剪策略复杂度不低（`layered` 与旧的 `legacy` 两套并存，可随时回滚）。之所以值得，是因为简单截断会删掉用户的硬约束（比如预算改了以后，模型还在按旧预算搜），这类错误用户能直接感知，而 token 超限只是成本问题。

## 二、记忆：存事实，不存结论

偏好分两类处理：

- **正向偏好**（「我喜欢轻便的」）：先由模型提炼去噪，再连同向量**原子持久化**，每轮按语义召回
- **负向约束**（「不要黑色」）：**全量保留**，不走召回——负面约束一旦漏掉，用户会立刻觉得「它没听我的」

注入方式是通过 AgentScope 的 Middleware，在每轮以独立 hint 注入，不混进对话历史。

**关键的取舍**：记忆用工具（记住/修改/删除）操作时要先过审批卡，用户点了「批准本次操作」才执行；拒绝则不改库。这牺牲了一点流畅度，换来的是记忆不会被模型误改——错误记忆比没有记忆更糟。

## 三、Skill：模型会执行的文本必须版本化

用户可以自己写 Markdown 步骤保存为个人 Skill，后续用 `/` 调起。问题在于：**Skill 是会被模型当作指令执行的**，如果页面显示的版本和实际执行的版本不一致，就是一个 prompt 注入面。

**做法**：服务端按版本号 + **内容哈希** 校验后才读取正文执行；元数据常驻上下文，正文按需加载。个人 Skill 只作用于当前买家，且只能指导已有工具的使用，不允许上传脚本或扩大工具权限。

## 四、并发：旧写不能覆盖新写

同一会话可能被多个请求同时推进：用户连点发送、刷新重连、自动化任务到点触发。

**做法**（`app/infrastructure/persistence/sql/session_store.py`）：Redis 租约负责**执行期互斥**，本地数据库维护 fencing epoch 负责**保存时校验**。旧 epoch 在取得新 epoch 时立即失效，因此被抢占的执行即使晚到，写入也会被 CAS 拒绝。

这里我没有用单纯的分布式锁，因为锁只能保证「同一时刻只有一个人跑」，保证不了「跑完的人是不是还有权写」。

## 五、检索与降级

链路：`embedding → Qdrant topK → reranker 精排`。

**两级降级**：reranker 不可用 → 退化为纯向量排序 → 再不可用退化为关键词召回。但正式评测门禁在发生降级时**直接阻断**——降级是为了不挂服务，不是为了悄悄降质上线。

值得注意的是 **BM25/RRF 混合检索已实现但默认关闭**。原因是实现不等于有收益，在没有数据证明它在当前商品目录上更好之前，打开它只是增加不确定性。等评测跑完再决定。

## 六、模型配置：执行要冻结

`ModelRegistry` 统一读内置目录与买家自定义连接。每个会话绑定模型，但**每轮执行会冻结一份快照**——生成过程中切换模型不会改变本轮行为，避免上下文与工具合同错配。切到更小的上下文窗口前会先检查已有上下文能否容纳。

密钥在服务端加密保存，不回显、不进入浏览器存储。

## 七、防止工具调用失控

- `LoopDetector`：用参数指纹识别重复的工具调用，避免模型在同一件事上来回转
- `CircuitBreakerRegistry` / `SharedCircuitBreakerRegistry`：工具级熔断，防止一个坏掉的外部依赖拖垮整轮
- `task_dispatch` 子 Agent：需要并行或上下文隔离的长链任务才派发，避免检索中间结果污染主 Agent 上下文

## 八、危险操作拆两步

交易不是「Agent 调一个下单函数就完了」：

1. Agent 或页面生成**确认单**（商品、数量、金额、收货信息）
2. 买家明确批准后才执行本地订单与库存事务（幂等键防重复提交）

自动化任务默认「自动开始」关闭，到点只生成待开始记录；下单、取消、改偏好仍需确认。连续三次失败暂停，避免无人值守时无限重试烧额度。

**说明**：商品来自版本化样例目录，订单是本地业务账本，未接入真实支付与物流。

## 九、评测

按「场景族」组织用例：六类（同义表达、多轮需求修改、反例与不适用条件、策略冲突、安全审批、版本撤回）× 100 条 = 600 条，开发集 240 条、留出集 360 条，同一场景族只进入其中一边，防止同族变体泄漏。

分两类计分：模型决策（真实调用）与数据库流程（真实接口 + SQLite）。

**一个没解决好的地方**：发布门槛目前还没有和真实评测报告强制绑定，也就是说评测能发现问题，但不会自动阻止不合格的版本发布。这是我知道但还没做完的部分。

## 十、技术栈

AgentScope 2.x / FastAPI / AG-UI（SSE + 游标重连）/ SQLite / Qdrant / Redis（可选）/ React 18 + TypeScript + Vite / OpenTelemetry（可选 Langfuse）。

## 本地运行

```bash
cp .env.example .env            # 填 LLM_API_KEY（OpenAI 兼容网关），不填无法启动
uv sync --frozen
npm --prefix frontend ci

# 终端 1：后端
uv run python -m uvicorn app.presentation.server:app --host 127.0.0.1 --port 8000

# 终端 2：前端
npm --prefix frontend run dev -- --host 127.0.0.1 --port 5173
```

最小模式只用 SQLite + 本地 Qdrant，不需要 MySQL / Redis / Docker。接口文档在 `http://127.0.0.1:8000/docs`。

测试：

```bash
uv run python -m pytest -q
npm --prefix frontend test
```
